# OpenCode Backend

Status: v1 built (epic E1, #117000). Sixth Backend: `HostBackend.opencode`, shown as "OpenCode". It serves OpenCode 2 only (floor 2.2.0; the executable pin lives only in `scripts/ci/opencode-contract.py`). Evidence is OpenCode 2.2.7 on Linux x64: the load-bearing facts O1–O26, with version, date and method, are in [`../research/opencode-v2-server-2026-11.md`](../research/opencode-v2-server-2026-11.md).

OpenCode 2 runs one shared background server per user, which also powers its TUI and web UI. It owns every session, durable in SQLite, and serves HTTP plus server-sent events on a loopback TCP port behind HTTP Basic auth. Waycar reaches that port through OpenSSH direct-tcpip on the Host's shared SSH connection, as the Ultimate Backend reaches its server. Like Codex (`codex-backend.md`) it is chat-first: a session has a transcript and structured requests, never a terminal of its own; a pane that shows the session's TUI is linked to it instead.

OpenCode 1 (npm `opencode-ai`) has no shared server and stays a terminal agent on the herdr and tmux Backends, as today. Both install a command named `opencode`; `opencode --version` tells them apart (O1).

## Shape

Decisions: Mike, card 1504 (2026-11-11): 1b, 2b, 3a, 4a, 5a; card 1530: 1a.

- **Shared server-Backend layer** (pick 5a): Codex and OpenCode share what a server-hosted chat runtime needs: the installed/stopped/running/starting state with **Start … server** in Host detail and New Agent, the chat-only capability gate (structured requests, Chat Mode always on), the linked pane behind Show Terminal, session-to-pane links, Closed Sessions resume, and the "Show … sessions" visibility preference. Codex moves onto it first, with no behaviour change; its tests guard the move. What stays per Backend: the wire protocol, auth, identity and origin, approval recovery and the launch. In code the layer is `ServerChatBackend` (`Sources/Waycar/Transport/ServerChatBackend.swift`: its per-Backend facts, `ServerRuntimePresence`, `HostBackend.isServerChat`), `ServerRuntimeState`, `ServerSessionLinks` (per-Backend command-line and origin link rules) and `HostServerRuntimeSection`; OpenCode adds a case there.
- **Detection** (O1, O2): the one detection exec adds `opencode --version` (with `~/.opencode/bin` on PATH, like `HerdrHostPath.extraPATH`). For `opencode v2.*` at or above the floor it also runs `opencode service status` and reads the URL, pid and version from `$XDG_STATE_HOME/opencode/service.json` (default `~/.local/state/opencode/service.json`). Nothing else: neither command starts a server. Never run `opencode api`, or any server-backed command without `--server` (O2, O3). The password is not part of detection and is never cached on the device.
- **Starting** (memory `no-auto-start-host-services`): OpenCode's own clients start the server, so on most Hosts that use OpenCode 2 it is already running (O3). Waycar never starts it on its own. Host detail shows "OpenCode server running" or "not running"; **Start OpenCode server** shows only there and in New Agent › OpenCode, never as a Console banner or row (as Codex, card 1224 3a). It runs `opencode service start`, in the macOS login session as a one-shot launchd job like Start Codex server, because every tool the server runs inherits its environment (O4).
- **Transport** (`Sources/Waycar/Transport/OpenCode/`): HTTP/1.1 over direct-tcpip to the registered URL's port (O5, O7) in the `.ordinaryForwarding` admission class, one channel per request, plus one long-lived `GET /api/event` stream per Host. The Ultimate Backend's HTTP client and SSE parser are shared and gain request headers and `PATCH`. Every request carries `Authorization: Basic` for user `opencode`; the password is read over SSH exec from the registration file when the transport opens, kept in memory only, and read again once on a 401 (O6). A Host refusing direct-tcpip (`AllowTcpForwarding no`, `PermitOpen none`) fails preflight with the same guidance as herdr.
- **Inventory** (pick 1b; O9, O10): every unarchived top-level session (`GET /api/session?parentID=null&archived=false`, paged by cursor, newest first, capped at 500) is an Agent, whoever started it. Pane id `opencode:<sessionID>`, one Workspace per `location.directory`, title as the Agent name. After the first read the event stream keeps it current: `session.created`, `renamed`, `archived`, `unarchived`, `deleted`, `metadata.updated`, `execution.*`, `permission.*`, `form.*`, `viewed`. The stream has no replay (O14): every (re)connect re-lists and re-reads `/api/session/active` and the pending requests of running sessions.
- **Archive and Closed Sessions** (card 1530 1a): sessions never unload, so the list shrinks only by archiving. The Agent's swipe and menu action is labelled **Archive** (never Close) and sends `PATCH /api/session/{id} {archived: true}`; the session also leaves OpenCode's own lists at the desk. Closed Sessions lists archived top-level sessions; Resume sends `{archived: false}` and opens the chat (and, on a Host with a visible terminal runtime, a linked `opencode --session <id>` pane, as New Agent does).
- **Status**: a session with a pending permission request or Form is Blocked; one in `/api/session/active` (or between `execution.started` and its end) is Working; an idle session whose last idle transition is newer than `time.viewed` is Done, otherwise Idle. Opening its Chat in Waycar marks it viewed (`POST /api/session/{id}/view`), as OpenCode's own clients do. Nothing comes from Waycar's Status Hooks: plugins run inside the shared server with the starting client's environment (O4, O21).
- **Requests** (pick 4a; O17, O18): `GET /api/session/{id}/permission` and `/form`. A `shell` permission shows on Chat Mode's **Needs your OK** card as a command, an `edit`/`write` permission as a file change with its resources as paths; Allow replies `once`, Cancel replies `reject`. A Form with `metadata.kind: "question"` shows as a **Needs your answer** card (fields `q0…`, options, typed text when `custom`); other Forms stay answerable on the Host. A 404 or 409 answer means it was answered elsewhere (`agent_request_resolved`). Answers need a live connection and are never queued. A server restart cancels pending requests (O20); the next re-read drops their cards.
- **Chat** (O13, O15, O16): `GET /api/session/{id}/message`, newest first, at most four pages: user prompts with their image files, each turn's text reply, tool calls as the Codex transcript shows them, and a failure card for an `idle` with outcome `failed`. Send is `POST /prompt {text, files}`; a prompt to a running session is steered into it by OpenCode. Stop is `POST /interrupt`; a prompt queued before Stop stays queued on the Host and goes out with the next one.
- **New Agent › OpenCode** (O11, O12): Waycar mints the session id in OpenCode's own format (`ses_` + its descending time prefix + random base62) and creates the session with `POST /api/session {id, title: <name>, metadata: {waycar: {launch, origin: "waycar"}}, location: {directory}}`. The create is idempotent, so the id is the Launch Tag: a lost answer is retried with the same id and never duplicates (memory `offline-launch-queue-semantics`). An optional first message goes as the first prompt. On a Host with a visible terminal runtime (Herdr TUI, then Herdr Core, then tmux) Waycar then opens `opencode --session <id>` in a new Workspace, linked and hidden; chat-only otherwise. Chat Mode on adds the Chat Prompt, as the session instruction entry `waycar-chat-prompt` (`PUT /api/experimental/session/{id}/instructions/entries/waycar-chat-prompt {value}`, which reaches the system prompt, O26), and the Settings › Chat Mode OpenCode model (`model: {providerID, id}` on create). The id is minted once, when the launch is first requested, and kept with its Queued Launch (`LaunchDraft.opencodeSessionID`); the first message goes through the Composer's queue, as for every Agent. A form try that failed after its create (the Chat Prompt write refused, say) leaves its session behind, so the form's Retry with the same inputs sends the same id and name again and finishes that session instead of minting another (B-40; `LaunchRetryIdentityMachine.retryingOpenCodeSession`, the one exception to a Retry being a new launch).
  - **Unverified below 2.2.7:** the Chat Prompt's instruction-entry endpoint (`/api/experimental/…`, O26) is verified only on 2.2.7, while the supported floor is 2.2.0. If 2.2.0–2.2.6 lack it, every Chat Mode launch there fails its write (and its Retry fails the same way), and the floor goes to 2.2.7, but only after a live check of those versions; the floor is unchanged until then.
- **One card per session**: the session card is the Agent. A pane known to show it is hidden from its terminal Backend's list and opens from Show Terminal. Waycar knows the link from its own launch, else from `opencode --session <id>` / `-s <id>` in the pane's command line, else from a one-to-one same-folder match between an unlinked OpenCode 2 pane and an unlinked desk session (`metadata` without `waycar`); never a Waycar-tagged one. Without a sure link both cards show. Archive leaves the TUI running, so a pane surely linked to an archived session (its launch marker or command line) stays hidden, and Resume shows the session in that pane again; it opens a new pane only when none is left. The folder match never looks at archived sessions (an old one would hide a fresh TUI), so Archive first pins a pane linked by folder alone to its session with the plain marker a New Agent pane gets (`ConsoleStore.pinFolderLinkedTerminal(of:)`, card 1611 2a): it hides with the session and comes back with it on Resume, and the marker leaves with the pane's Agent. Archive never closes the pane. The swipe disc is an archive box on system indigo (`Color.indigo`; the brand `indigo` token is the gradient's middle stop only), as Mail's Archive, with red kept for Close.
- **Terminal launches on OpenCode 2 Hosts**: the Chat Mode `-m` flag does not exist on V2 (O12) and is left out there (launches and Closed Session resumes). A launch of kind `opencode` mints a session id and opens `opencode --session <id>`, unless the user's arguments pick a session, `--continue`, `--standalone`, `--server` or a subcommand; while the server runs and the folder is known (not a new Worktree) it creates that session first, as New Agent › OpenCode does, and its Chat Marker names the session, so the pane links on herdr too; the Host Tools read V2 transcripts through `opencode session export --server` (task E1.1, Host Tools 2.4.1), never the plain form, which starts the server (O2). When the server is stopped, such a pane's own TUI starts it, exactly as `opencode` at the desk does: that is the user's explicit launch, not Waycar starting a service (New Agent › OpenCode and Resume still require a running server).
- **Push** (pick 3a; O21): Host Tools ship a V2 server plugin (the existing `waycar-agent-state.js`'s empty V2 `setup()` becomes it) that subscribes to `permission.asked`, question `form.created` and `session.execution.succeeded`/`failed`, and posts needs-your-OK, question and Done notifications as `opencode:<sessionID>`, once per event: every loaded Location runs its own plugin instance and each sees every event. `opencode_enabled: false` in `notify.json` silences them. Live Activities and Apple Watch include the Console's OpenCode rows.

## Risks

- The API calls itself experimental (`0.0.1`) and changes fast (O24). The contract check fails CI on drift; the app parses leniently.
- A newer TUI restarts the shared server on its first launch (O20): running turns resume, pending approvals are cancelled and may be asked again.
- Under pick 1b a busy Host lists many sessions; paging and the 500 cap bound the cost.
- The password lives on the Host in a mode-600 file; Waycar reads it as the same user and keeps it only in memory.
- Hosts need `AllowTcpForwarding local` or `yes`, and `PermitOpen` must allow the port.
