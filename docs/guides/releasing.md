# Releasing

One command cuts a release:

```sh
make publish                    # patch bump from the newest released version
make publish VERSION=0.2.0      # explicit version
make publish DRY_RUN=1          # print the plan, change nothing
make publish YES=1              # skip the confirmation prompt
```

Options are make variables rather than flags because make consumes
`--dry-run` as its own `-n` and rejects unknown long options, so a flag
never reaches the recipe.

`scripts/publish.sh` is the implementation; this document is the contract.

## CHANGELOG.md is the source

Every change lands under `## [Unreleased]` in `CHANGELOG.md` as it
merges, so cutting a release is a mechanical move rather than archaeology
over `git log`. That section names what ships and becomes the release
notes verbatim — in the plan preview and in the GitHub release body.

Entries are public: waycar.dev/changelog and the app show them verbatim,
so write them for users and keep internal paths, ADR numbers, hostnames
and real user or customer data out of them. Issue and PR references are
fine; both surfaces strip them.

An empty `[Unreleased]` means there is nothing to release: `make publish`
aborts and says so. The convention was not followed, and that gap is the
finding; synthesizing notes from commits would bury it.

## One file per release

Released versions live in `apps/web/src/content/changelog/<X.Y.Z>.md`,
one file per release, and `CHANGELOG.md` keeps only its header and
`[Unreleased]`. A release file is front matter, a blank line, then that
release's former `[Unreleased]` body verbatim. The history starts at 1.0.1
(2026-09-28) by choice; don't backfill older releases.

A release file looks like this:

```markdown
---
version: 1.1.3
date: 2026-10-04
---

### Added

- **Last screen while reconnecting**: ... (#105)
```

`make publish` writes the file; never write or rename one by hand. The
file name and its `version` must agree, or publish refuses to run.
waycar.dev/changelog (rebuilt on every push to `main` that touches
`CHANGELOG.md` or the release files) and the app's Settings › About ›
Changelog (bundled at build time) both show `[Unreleased]` first when it has an
entry, titled Unreleased, then every release newest first. Both strip
issue and PR references such as `(#105, refs #27)` when they render,
because they point into the private repository; the files keep them.

## Declared and derived

One place *declares* the version. Everything else is derived and belongs
to the tool that produced it:

| File | Role |
|---|---|
| `project.yml` → `MARKETING_VERSION` | **declared** (app + notification extension, in lockstep — App Store validation rejects a bundle whose appex versions differ) |
| `project.yml` → `CURRENT_PROJECT_VERSION` | incremented every publish; App Store Connect rejects a reused build number |
| `Waycar.xcodeproj/project.pbxproj` | derived — regenerated by `xcodegen generate` |
| `Sources/WaycarNotificationService/Info.plist` | derived — its version keys are `$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)` references |

`relay/package.json` is `"private": true`. A
package that is never published declares nothing, so its `version`
field is not part of an app release and `make publish` leaves it
alone. The plugin has its own release rule (see The Waycar plugin, at
the end).

## Version resolution

1. An explicit `VERSION=` wins. A leading `v` is stripped; anything that
   is not `X.Y.Z` is rejected (prereleases are out of scope).
2. Otherwise the newest released version, the highest `version` (compared
   numerically) in the release files' front matter, has its patch
   segment incremented.
3. That version is cross-checked against the newest `vX.Y.Z` git tag. If
   they disagree, publish aborts — one of them is lying, and guessing
   which is how a release gets cut from the wrong base.

With neither a release file nor a tag (the state before the first
release) there is nothing to bump from, so the first version must be
passed explicitly.

## What `make publish` does, in order

1. **Preflight.** Tooling present (including `python3` and `openssl`)
   and `gh` authenticated; `ASC_API_KEY_ID` and `ASC_API_ISSUER_ID` set
   and `~/.appstoreconnect/private/AuthKey_<ASC_API_KEY_ID>.p8` present
   (step 10 needs them; `make upload` would otherwise fall back to the
   Xcode account and the release would ship without reaching testers);
   clean tree; on `main` and level with `origin/main`; `[Unreleased]`
   non-empty; no release file for the target version yet; the target tag
   absent locally *and* on the remote — a local-only check passes right
   up until the push fails, by which time the release commit has already
   landed. Finally, the maintainers' demo Host check (kept in ops) must pass
   on the owner's Mac; a failure stops before release edits, build or
   upload. Then `make review-smoke` must pass too: the release as a
   reviewer's device installs it (see
   [Reviewer-device smoke run](#reviewer-device-smoke-run)),
   with the same stop on failure. `DRY_RUN=1` lists both checks without
   running either.
2. **Print the plan and ask.** Resolved version, every file it will
   touch, every command it will run, and the release file it will write,
   whose body is the release notes. `DRY_RUN=1` prints exactly this and
   exits without touching anything.
3. **Cut the CHANGELOG.** The `[Unreleased]` body moves into a new
   `apps/web/src/content/changelog/X.Y.Z.md` with today's date, leaving
   an empty `## [Unreleased]` in `CHANGELOG.md`.
4. **Update the declared version** and increment the build number, in
   every target.
5. **Regenerate** `project.pbxproj` via `xcodegen generate`.
6. **Build and upload** — `make archive ADMIN_BUILD=` then `make upload`,
   which signs locally and uploads to App Store Connect. The archive never
   includes the admin panel (see below).
7. **Commit** as `chore: release vX.Y.Z`, the new release file included.
8. **Push the commit, then create and push the annotated tag.** In that
   order: the tag has to point at a commit reviewers can fetch.
9. **Create the GitHub release** with the `[Unreleased]` body as its
   body, then verify it is published and not a draft.
10. **Distribute to Waycar Testers** — `make distribute`
    (`scripts/asc-distribute-build.py`) waits for App Store Connect to
    process the uploaded build, polling for up to 45 minutes, then adds
    it to the internal Waycar Testers group. That group has no automatic
    distribution, so without this step the release build never reaches
    TestFlight testers, and the pre-submission device check must run on
    this exact build: the non-admin build App Review gets. Needs
    `ASC_API_KEY_ID`/`ASC_API_ISSUER_ID` and the key (App Store Connect
    scripts, below).

The build runs before anything is committed on purpose. It is the
slowest and most failure-prone step (codesigning, network, App Store
Connect auth), and a failure there leaves nothing but local file edits,
which the script tells you how to revert.

The release commit goes straight to `main`, also on purpose: it is
mechanical, was reviewed line by line in the plan, and the tag must
point at the exact SHA on that branch — a PR merge would change it.

Distribution runs last, also on purpose: it can wait up to 45 minutes,
and `main` may move in that time, so the release commit and tag are
pushed first.

### If it fails after the tag is pushed

Do not re-run `make publish`; the tag exists and preflight will refuse
it. Recovery is `gh release create` against the existing tag, then
`scripts/asc-distribute-build.py <build>`; the script prints both.

### If distribution fails

The release is complete: commit, tag and GitHub release are all
published. A failed or timed-out distribution (or Ctrl-C while it
waits) only means the build is not in Waycar Testers yet; `make publish`
exits non-zero and prints the command. Do not re-run publish. Once App
Store Connect shows the build, run
`scripts/asc-distribute-build.py <build>` with the build number it
printed (the `CURRENT_PROJECT_VERSION` of the release commit).

## App Store Connect handoff

`make publish` uploads the build. Staging the App Store version in App
Store Connect (the build, What's New, the review information) and
submitting it are the maintainers' steps, kept with the App Store material
in ops. What's New covers everything since the last release that reached
users, at most 4,000 characters, written for users like the changelog.
Once the version is live, merge any site copy held for it and set
`REVIEW_SMOKE_PREVIOUS` in the `Makefile` to its tag.

## Reviewer-device smoke run

`make review-smoke` (`scripts/review-smoke.sh`, on a Mac, about 15 min the
first time) runs the release the way a reviewer's device gets it: on a device
and OS version the regular tests never use, as an update over the previous
approved version.

1. **Release build.** Builds the Release configuration for the simulator
   with `ADMIN_BUILD=` (no admin panel), as `make archive` builds it for
   `make publish`, plus the walkthrough UI test
   (`Tests/WaycarScreenshots/ReviewSmokeTests.swift`).
2. **Previous release.** Builds `REVIEW_SMOKE_PREVIOUS` (a tag, set in the
   `Makefile`: the last App Store-approved release) with that tag's committed
   project, from a `git archive` of the tag in `REVIEW_SMOKE_REPO` (default:
   this checkout; point it at a clone that has the tag when this one does
   not) in a temporary folder, which it removes. The app is cached in
   `~/Library/Caches/waycar-review-smoke/<tag>/`, so later runs skip the
   build. If a newer Xcode can no longer build the tag, run
   `make review-smoke REVIEW_SMOKE_PREVIOUS=` (fresh install only) and say so
   in the handoff.
3. **Reviewer simulators.** `Waycar Review iPhone` (iPhone 17 Pro Max,
   iOS 27.2) and `Waycar Review iPad Air` (iPad Air 5th generation, iOS 26.4,
   an older iPadOS than the shared set's). It creates
   them when missing, leases both in one `scripts/sim-slot.py` call, and
   releases and deletes them when it ends, pass or fail. It never installs a
   runtime: a missing one stops the run.
4. **Update, then walkthrough**, on each simulator in turn: install and
   launch the previous release, install this build over it (the files the
   old app wrote must survive), then run the walkthrough through
   `scripts/run-app-simulator-tests.py`, launched with no arguments: the
   analytics question (declined), the first-run screen, the Sample Host, an
   Agent and back, New Agent (+) and its sheet closed, on the iPad a rotation
   to landscape and back, then the Sample closed and the first-run screen's
   Settings: CarPlay Voice listed exactly where `CarPlaySupport.isAvailable`
   says (the iPhone on iOS 26.4+, never an iPad), no Admin, About, Help.
   A warm-up test runs first on both simulators without launching the app:
   the first UI test on a freshly booted simulator fails at its first query
   (kAXError -25218).
5. **Video.** Each walkthrough is recorded to
   `build/review-smoke/iphone.mp4` and `build/review-smoke/ipad.mp4` (H.264,
   no audio), to look at afterwards.
6. **Result.** A summary per device (runtime, old → new version, pass or
   fail, video) and the Waycar crash reports any of the run's simulators left
   since it started; any failure or crash report exits non-zero. Logs and
   result bundles stay in `build/review-smoke/`.

## App Store Connect scripts

All of them use `scripts/asc_client.py`, which signs the API token from
`ASC_API_KEY_ID`, `ASC_API_ISSUER_ID` and the `.p8` key (at
`ASC_API_KEY_PATH`, by default
`~/.appstoreconnect/private/AuthKey_<ASC_API_KEY_ID>.p8`). It loads
`~/.env` when present, because a non-interactive SSH session does not.
Requests time out after 30 s; a GET that hits a temporary error (HTTP 5xx
or 429, a dropped connection) is retried with backoff, and a POST is sent
again only after a check shows it did not land. App Store Connect answers
routine reads with HTTP 500 a few percent of the time. The scripts run on
the Mac's own `/usr/bin/python3` (3.9), so they use nothing newer.

- `scripts/asc-newest-build.py` prints the newest uploaded build number
  (the TestFlight workflow numbers past it).
- `scripts/asc-distribute-build.py <build>` waits for processing and adds
  the build to Waycar Testers (`make distribute`).
- `scripts/asc-review-state.py --once` prints the newest App Store version,
  its `appStoreState` and `appVersionState`, and the latest review
  submission's state. Without `--once` it watches for an Ultimate script
  automation: silent until the state changes, then one
  `FIRE <version> <old> -> <new>` line; `DONE` once the version is approved
  or rejected, or the deadline (`--deadline`, default 3 days, failed checks
  included) passes. Its state lives in `$AUTOMATION_STATE`. The API key is
  on the Mac, so from the agent host pass `--ssh mac`: each check then runs
  on the Mac without a checkout there.
- `scripts/test-asc-scripts.py` tests the client and the watch with stubs
  (CI runs it).

## Publish mode: local build

The archive is signed with the developer's Apple credentials and
uploaded to App Store Connect. Neither exists on a CI runner here, so a
tag-triggered workflow cannot produce the artifact and there is no
release workflow to keep in sync.

The GitHub release therefore carries the notes and the tag only. There
is no downloadable asset: an App Store-signed `.ipa` installs nowhere,
and the build reaches testers through TestFlight.

## `make publish` versus `make bump && make testflight`

Two paths to TestFlight, different jobs:

- `make bump && make testflight` — an **interim** build for testing on
  device. Bumps the build number only; the marketing version, the
  CHANGELOG, and the tags stay where they are. Leaves `project.yml` and
  `project.pbxproj` dirty for you to commit; land that commit right after
  the upload, since until `main` has it the next interim build takes the
  same number and App Store Connect rejects it. After uploading it runs
  `make distribute` (`scripts/asc-distribute-build.py`), which waits for
  App Store Connect to process the build and adds it to Waycar Testers;
  that group has no automatic distribution, so an upload alone never
  reaches testers. Needs `ASC_API_KEY_ID`/`ASC_API_ISSUER_ID` and the key.
- `make publish` — a **release**. Everything above, in one shot, with a
  version, notes, a tag, and a GitHub release; its non-admin build goes
  to Waycar Testers the same way.

Once a marketing version's App Store version is closed for uploads (for
example 1.1.3 after submission), interim builds still carry that version and
App Store Connect rejects them with ITMS-90062. Only `make publish`, which
cuts the next version, can upload again.

Never hand-edit `MARKETING_VERSION` to cut a release; that is what
publish is for.

## The admin panel is for interim builds only

Settings › Admin (the Review Prompt test controls; ADR 0032) and the
internal-only network analytics exist only in binaries compiled with the
`WAYCAR_ADMIN` Swift condition, plus every Debug build:

- `make testflight` and the CI TestFlight workflow archive with
  `ADMIN_BUILD=1`, which sets the `WAYCAR_ADMIN_CONDITION` build setting
  to `WAYCAR_ADMIN`.
- `make publish` archives with `ADMIN_BUILD=` whatever the environment
  says, so a release build has no admin panel.
- **Submit only a `make publish` build to the App Store.** An interim
  TestFlight build carries test tooling and sends analytics the App Privacy
  answers do not declare.

## What's New notes on TestFlight builds

Each TestFlight build CI uploads (`.github/workflows/testflight.yml`)
carries short What's New notes, shown once after the tester updates.
`scripts/whats-new.py` builds them before the archive:

- **Range.** Everything since the previous CI build: the highest build
  number below this build recorded in a `refs/notes/whats-new` note
  whose commit is an ancestor of the tested commit. With no such note,
  the last 30 first-parent commits.
- **Input.** The curated notes first: the lines added in that range to
  `CHANGELOG.md` and to the release files, so an entry added and released
  between two builds still counts. Entries a release only moved out of
  `[Unreleased]` (already there at the range's start) and the release
  files' front matter are left out. Then commit subjects and bodies fill
  gaps.
- **Summary.** An LLM through OpenRouter returns at most five
  one-sentence bullets, each with an SF Symbol from a fixed allowlist.
  The default model is `z-ai/glm-5.3-flash`; the repository variable
  `WHATS_NEW_MODEL` (or `--model` locally) overrides it with any
  OpenRouter model that supports structured outputs. The key is the
  `OPENROUTER_API_KEY` repository secret (`gh secret set
  OPENROUTER_API_KEY`). The script re-validates the bullets before
  writing `Sources/Waycar/Resources/WhatsNew.json` in-tree; it is not
  committed back.
- **History.** After the build reaches the Waycar Testers group, CI
  attaches this build's entry (compact JSON: build, date, items) as a
  git note on the tested commit under `refs/notes/whats-new` and pushes
  that ref. Up to nine earlier notes ride along, so a tester who skipped
  builds sees each one they missed. Notes, not tags: GitHub refuses to
  let the workflow's token create a tag on a commit whose history
  touches `.github/workflows/`, and a notes ref's commits contain only
  note blobs, so that check never applies.

If the key is missing or the model call fails after one retry, the build
ships with the history only, CI logs a warning, and no note is recorded —
the next build's range then covers the missed changes. Notes never block
an upload.

To see the recorded notes (clones do not fetch notes by default):

```sh
git fetch origin refs/notes/whats-new:refs/notes/whats-new
git log --notes=whats-new
```

Local `make testflight` and `make publish` builds bundle the committed
empty seed (`{"builds": []}`), so they show no What's New sheet.

Preview what CI would produce (writes nothing; fetch the notes first so
the range and history match CI):

```sh
OPENROUTER_API_KEY=... scripts/whats-new.py --build <N> --out /tmp/x.json --dry-run
```

CI also passes `--note-file <path>`, which writes this build's entry
for the note; it is written only when the summary succeeds.

## The Waycar plugin

The plugin versions independently of the app. `plugin/herdr-plugin.toml`
and `plugin/Cargo.toml` declare it and carry the same value; `Cargo.lock`
follows (`cargo update -p waycar --offline` in `plugin/`).

- **Every change to a file the plugin package ships bumps the version**:
  patch for fixes, minor for new behavior. "Ships" follows
  `scripts/package-plugin.sh`: `bin/`, `hooks/`,
  `herdr-plugin.toml`, `install.sh`,
  `test-vectors/tmux-pane-options-v1.json`, the Rust sources (`Cargo.toml`,
  `Cargo.lock`, `rust-toolchain.toml`, `rust/`),
  and `scripts/package-plugin.sh` and `scripts/build-plugin-binaries.sh`
  themselves. The plugin's `README.md`, `LICENSE`, `NOTICE` and dev-only
  dependency churn are exempt.
- **Every version bump also sets `WaycarPluginRequirement.currentVersion`**
  to the same value. Host detail shows a Host at or above its minimum but
  below it as "<version> available" with the update button: an offer, with
  no warning, no Console row and no gate. Never raise a minimum for it.
- **An app change that relies on new plugin behavior raises
  `WaycarPluginRequirement.minimumVersion`**
  (`Sources/Waycar/Transport/WaycarPlugin.swift`) in the same PR. The app
  prompts the user to update any Host whose plugin is older.
- **`scripts/check-plugin-version.sh` guards this** in CI, and
  before `web.yml` deploys and `plugin-release.yml` tags: the version
  fields and `currentVersion` agree, the minimum is not above the plugin
  version, and shipped files are unchanged since the released version. "Released" is the
  `plugin-v<version>` tag, or, before that tag exists, the baseline commit
  (`PLUGIN_BASE`: the PR base or the push's previous commit in CI,
  `origin/main` locally) when it already declares this version. A missing
  or all-zero baseline falls back to the tag alone, with a note.
- **`WaycarPluginRequirement.nativeToolsMinimumVersion` prompts, it never
  gates.** A Host on a Node-era plugin (below the constant, 2.0.0 the first
  native one) gets a Console row, and Host detail an update button, that run
  the same update the app already has; chat, push and the rest stay on at any
  version `minimumVersion` allows. Do not raise `minimumVersion` for it. Not now
  is kept per Host and per value of the constant: 14 days, back once, then
  never, and the Host's "Remind me" switch off hides it. The guard script
  checks it like the other minimums, so an app build that prompts cannot merge
  before the plugin it asks for is on `main`, and it must not ship before
  waycar.dev serves that plugin (below).
- **`scripts/check-deployed-installer.sh` runs before any app submission**
  (`make archive`, so `make testflight`, `make publish` and the TestFlight
  workflow): the `install.sh` waycar.dev serves today must carry a plugin
  version at least every minimum in `WaycarPluginRequirement` and its
  `currentVersion`. Otherwise the update the prompt or offer starts would
  reinstall the older package and the prompt would stay. It fails by design until the plugin release that the constant
  names is deployed.
- **Releasing is merging.** On a push to `main` that touches `plugin/`,
  `.github/workflows/plugin-release.yml` cuts `plugin-v<version>` with the
  four per-target tarballs (native `bin/waycar`, built by
  `scripts/build-plugin-binaries.sh` inside `scripts/package-plugin.sh`), their
  checksums and the rendered installer when the version is
  new (a no-op otherwise), and `web.yml` redeploys waycar.dev, whose
  `install.sh` always serves `main`'s plugin.
