# Waycar

Native iOS and iPadOS companion app for herdr (https://herdr.dev), tmux and herdr-core: an agent console over SSH, not a terminal app. Read `CONTEXT.md` for vocabulary and `docs/adr/` before challenging architecture decisions — the transport design in particular was reached after eliminating several dead ends. `README.md` has the repository layout, `CONTRIBUTING.md` how to build, test and send a change.

This file is the working guide for people and coding agents alike: the architecture, the facts about herdr, tmux, SSH and mosh that were expensive to find out (each with its version and method), and the conventions the code follows.

## Simulators (shared Mac)

- Many agents share this Mac; each booted simulator costs 2–5 GB and ~230 processes, and too many at once makes tests flaky. `scripts/sim-slot.py` caps booted simulators machine-wide (`WAYCAR_SIM_SLOTS`, default 4) and queues the rest FIFO.
- Never boot a simulator yourself (`simctl boot`, `open -a Simulator`, direct `xcodebuild test` against a shut-down simulator — xcodebuild boots it). The simulator make targets (`test-app`, `test`, `test-ipad`, `screenshots`, `sim`, `sim-ipad`, `sim-id`) queue automatically; anything else runs `scripts/sim-slot.py acquire <UDID|name>` first. It prints the UDIDs it granted, one line per distinct simulator in target order: a target repeating another, or a generic destination, adds no line, so a caller that reads lines by position checks it got as many as it needs.
- `make test-ci-app` and the `Waycar CI` simulator manage their own claim: never `acquire` or `release` them. When a live run holds `Waycar CI`, `make test-ci-app` (and CI) waits for it, saying once a minute who holds it, and gives up after `WAYCAR_CI_SIM_WAIT_SECONDS` (default 2700, 45 min); never create another or pin a shared simulator, whatever the script suggests.
- `make review-smoke` and the `Waycar Review iPhone` (iPhone 17 Pro Max, iOS 27.2) and `Waycar Review iPad Air` (iPad Air 5th generation, iOS 26.4) simulators manage their own lifecycle: it creates them when missing, acquires both in one call, and releases and deletes them when it ends, pass or fail. Never acquire, boot or delete them yourself; they are not part of the shared set. Run one `make review-smoke` at a time on the Mac.
- The shared set, all on iOS 27, is three iPhone 17 Pro Max (`SIM` and `SCREENSHOT_SIM`) and two iPad Pro 13-inch (M5) (`SIM_IPAD`), never fewer than two of each: `<model>` plus copies named `<model> 2`, `<model> 3`. `Waycar CI`, CI's own Pro Max (`make test-ci-app` creates it), is not part of it. Only a base model name (`SIM`, `SCREENSHOT_SIM` and `SIM_IPAD` as shipped) or a `name=` destination for one grants any free simulator of that model; a copy's own name, a UDID, or an `id=` destination grants exactly that simulator, so never set `SIM` to a copy's name. Screenshots need the Pro Max's 1320×2868, and any copy of it qualifies. `make sim-pool` recreates missing copies; otherwise never create a simulator or install a runtime except for the bug exception below.
- iPhone + iPad: acquire both in one call (`scripts/sim-slot.py acquire <iPhone> <iPad>`); never hold one while waiting for the other.
- Run the make target in the background and keep working on everything that needs no simulator (`make test-swiftmosh` on the host, code review, writing tests, docs). `test-app` compiles before it queues; once it has the slot it rebuilds only what changed meanwhile, then tests the current checkout. The slot stays held until you run `make sim-release`.
- After acquiring, address simulators by the UDID `acquire` printed, not by name (a name can map to any copy). The idle check below can't see hands-on use (Simulator.app, Xcode's debugger), so during long manual checks re-run `scripts/sim-slot.py acquire <UDID>` at least every 10 min to renew your lease.
- Release as soon as simulator work is done: `make sim-release`. Don't hold a simulator while coding or reviewing; the targets queue again when you need one.
- App test runs check for crashes when they end: `scripts/run-app-simulator-tests.py` (`make test-app`, `make test`'s app suite, `test-ipad`, `screenshots`, CI app lanes) prints the Waycar crash reports (`~/Library/Logs/DiagnosticReports/*.ips`) that the run's simulators left, grouped by cause, and fails the run if there are any. A simulated report (header `is_simulated`, such as `ExcUserFault_*`: a fault the system logged while the process kept running) is printed as a note and does not fail it. The WaycarSSH package tests and runs stopped by a signal are not checked. A crashed test host relaunches, so one bug can leave many reports. Investigate every reported crash before calling work done. To check by hand: `scripts/check-crash-reports.py --since <start> --udid <UDID>`.
- While another worktree is refused a slot, a simulator idle for 10 min (`WAYCAR_SIM_IDLE_MINUTES`; idle = no host process names its UDID, or `name=` for an unleased one, counted from your last `acquire` at the earliest) is shut down; re-run your target to queue again.
- `make sim-status` (read-only) shows the cap, holders, and queue. Never shut down or delete a simulator another worktree holds.
- Stuck in the queue (waiting long, or `acquire` timed out): run `make sim-doctor`; never bypass the queue. It says why the queue waits, and it applies only safe fixes. It frees leases whose worktree is gone, and idle ones only while another worktree waits, so run it while your `acquire` still queues. It kills a `simctl diagnose` tied to a leased simulator once it and its child processes have used no CPU for 3 min (waiters' polls and earlier doctor runs keep that clock) while its test run idles; when it reports a shorter quiet time, run it again later. It shuts down an unleased simulator that is stuck booting, or that fails its health probe on two doctor runs 2 to 15 min apart, so the next grant boots it fresh, unless an app runs in it. It can't see Simulator.app showing only a system screen, so acquire any simulator you use by hand: a leased one is never restarted. It never touches a test that is using CPU or `Waycar CI`. Waiters refused for 5 min run it themselves, at most once per 5 min across the Mac. Tell the user what it found and did, plus `make sim-status`.
- Bug exception: when a specific bug reproduces only on another iOS version or device model, create `Waycar #<issue> <model>` on the runtime it needs (`xcrun simctl create '<name>' '<device type>' <runtime id>`; omit the id and simctl picks iOS 27). When your task is done, delete it (`xcrun simctl delete <UDID>`). If `xcrun simctl list devices` then shows no other `Waycar #…` simulator on that runtime and it isn't iOS 27, also delete the runtime (`xcrun simctl runtime delete <id>`) and the stock simulators it came with, by UDID. Never delete the shared set, the iOS 27 runtime, or another worktree's simulator.

## Architecture

- **Stack**: SwiftUI, iOS 18+, iPhone + iPad. SSH via the repository-local `Packages/WaycarSSH` (libssh2 + OpenSSL), terminal rendering via the repository-local `Packages/GhosttyTerminal` (vendored libghostty-spm Swift layer over its checksum-pinned prebuilt core). See ADR 0001 (native stack), ADR 0003 (the superseded Dictation-era target raise), and ADR 0004 (terminal engine).
- **Transport**: herdr's JSON API (NDJSON over a remote Unix socket) reached through OpenSSH direct-streamlocal channels onto the socket itself — no socat, and no Host-side prerequisite beyond SSH access and a running herdr. A server that denies stream-local forwarding fails preflight rather than falling back. Interactive terminals request a PTY and exec `herdr agent attach` on it. See ADR 0011, which supersedes ADR 0002.
- **tmux backend** (ADR 0026, `docs/design/tmux-backend.md`): tmux 3.2+ is a second Backend, detected per connection (`HostBackend`). `TmuxTransport` (`Sources/Waycar/Transport/Tmux/`) speaks control mode (`tmux -u -C attach`) on a non-PTY duplex exec channel, matches reply blocks FIFO, and gets topology plus Agent Status from one `refresh-client -B` subscription over the `@waycar_*` pane options the Status Hooks write. A Host with both Backends shares one SSH connection (`HostSSHSession`) and keeps one projection per Backend (inventory, connection status), merged into one Console list. Attach execs a grouped-session chain on a PTY (never `-d`, never `refresh-client -C`).
- **herdr-core backend** (ADR 0031, `docs/design/herdr-core-backend.md`): herdr-core 0.1.10+ is a third Backend (`HostBackend.core`). `CoreTransport` (`Sources/Waycar/Transport/Core/`) speaks the framed `herdr-core connect` protocol on one non-PTY exec channel in the `.core` admission class. Attach is a PTY exec of `herdr-core attach`, with no takeover. Workspaces, Tabs and Panes are synthesized from core's terminals (`hc:` ids), and Agent Status comes only from what agents report to core (OSC 7501), never from Waycar hooks. Run `herdr-core`, never bare `hc`. Since every `hc` subcommand but `--version` starts a core, the connect and attach lines first probe core's socket with a plain connect (`CoreConnectCommand.socketScript`/`runningProbeScript`, mirroring the plugin's `running_core`: Perl, else Python off macOS, else only a socket-file test, which a stale socket passes) and exit 125 (`.coreNotRunning`) instead of starting one; only the user's **Start Herdr Core** or a found Install herdr-core starts it (`herdr-core server status`, in the macOS login session like Start Herdr TUI; #389).
- **Codex backend** (`docs/design/codex-backend.md`): Codex 0.167.0+ is a fifth Backend (`HostBackend.codex`). `CodexTransport` (`Sources/Waycar/Transport/Codex/`) speaks JSON-RPC over a WebSocket on the shared app-server's Unix control socket, reached through direct-streamlocal in `.ordinaryForwarding`, on the Host's shared SSH connection. Loaded top-level threads become chat-first Agents (`codex:<threadId>`), grouped by folder; status, transcript and structured approvals come from the server, never screen scraping or pane hooks. Detection starts nothing; only **Start Codex server** starts it, in the logged-in session on macOS. New Agent starts a thread and, on a Host with a visible terminal Backend, a linked `codex resume <id>` Workspace; the terminal is hidden from the list and opens through Show Terminal. Terminal-Backend Codex launches keep `--no-daemon` and stay separate.
- **OpenCode backend** (`docs/design/opencode-backend.md`): OpenCode 2.2.0+ (npm `@opencode/cli`, Homebrew `opencode`; OpenCode 1 stays a terminal agent) is a sixth Backend (`HostBackend.opencode`). `OpenCodeTransport` (`Sources/Waycar/Transport/OpenCode/`) speaks HTTP and server-sent events to the shared server's loopback port, reached through direct-tcpip in `.ordinaryForwarding`, with Basic auth from the Host's registration file (read over SSH exec, kept in memory only). Every unarchived top-level session is a chat-first Agent (`opencode:<sessionId>`), grouped by folder; status, transcript and structured approvals and questions come from the server. Codex and OpenCode share one server-chat layer (`ServerChatBackend`). Detection starts nothing; only **Start OpenCode server** starts it. New Agent mints the session id (the Launch Tag) and, on a Host with a visible terminal Backend, opens a linked `opencode --session <id>` Workspace; Archive replaces Close, and Closed Sessions lists archived sessions.
- **Zellij backend** (`docs/design/zellij-backend.md`): Zellij 0.46.0+ is a seventh Backend (`HostBackend.zellij`, label "Zellij", after tmux). Zellij has no control mode and no change push to CLI clients, so `ZellijTransport` (`Sources/Waycar/Transport/Zellij/`) runs one non-PTY exec in the `.zellij` admission class: a POSIX `sh` loop (`ZellijWatchCommand`) that prints `zellij ls -n` (ages replaced by a fixed ` [Created]`), each live session's `action list-panes -j` (folded to one line, cursor removed) and the Host Tools' per-pane state documents, only when they change, a newline otherwise, and ends its whole process group on stdin EOF (`kill 0`). Everything else is a one-shot `zellij -s <session> action …` exec with the detected absolute path. Session → Workspace, tab → Tab, terminal pane → Pane, pane ids `zellij:<session>/terminal_<n>` (shared with Host Tools and push). Status: the agent's own OSC 7501 record (`program_status` root, never `attention`), then the hook document, then screen detection, else Unknown. Attach opens the session oversized with `options --default-mode normal`, claims the phone with Ctrl g (to Locked), moves only the phone with `go-to-tab-by-id`/`focus-pane-id`, verifies with `list-clients` (restoring a desk that moved instead), then resizes. New Agent opens a tab in a session that has a client, otherwise a background session (`attach -b`), tagged `WAYCAR_LAUNCH=<tag>` in the command line. Zellij's saved (`EXITED`) sessions are Closed Sessions: Resume (the user's tap) is the only thing that ever attaches one.
- The UI layer must depend on a transport abstraction (protocol), never on an SSH library's types directly.
- Sibling deliverables live in this repo: `plugin/` is the herdr plugin (id `waycar`, action `waycar.pair`, installed from `https://waycar.dev/install.sh`) that renders Pairing Codes and posts Agent Notifications (a static Rust binary built from `plugin/rust`, no Node on the Host, `cargo test --locked` in `plugin/`); `relay/` is the stateless Push Relay it posts to, deployed at `https://waycar-apns.otreva.com` (dependency-free Node, `npm test`); `apps/` holds apps: today that is `apps/web/`, the marketing site at `https://waycar.dev` (Astro static build shipping only bundled same-origin scripts: CodeBlock's copy button, the help search palette and sidebar toggle, PostHog analytics, and the consent-gated Reddit and X ad pixels (third-party scripts, allowed in the Worker CSP); on Cloudflare Workers, deployed by `.github/workflows/web.yml`; `waycar.app` and the `www.` hosts 301-redirect to it). Help docs are one Markdown page per feature in `apps/web/src/content/help/` (served at `/help/<slug>`, rules in `apps/web/README.md` "Help docs"). The iOS app stays at the repo root until a second native app exists. iOS CI (`.github/workflows/ci.yml`) runs only on app/simulator paths; plugin, relay, and codegen drift (wire types, OMP demo terminal) run in `.github/workflows/ci-node.yml`; a marketing-site copy edit never starts either, except help pages (`apps/web/src/content/help/**`), which are bundled into the app and do run iOS CI. Wire types in `Sources/Waycar/Transport/Generated/` are produced by `scripts/generate-wire-types.py` from the committed schema snapshot `scripts/herdr-schema.json` — regenerate with `--schema scripts/herdr-schema.json` (the flag-less default shells out to a local `herdr` instead of the snapshot) rather than hand-edit; CI fails on drift via `--check`. The vectors in `plugin/test-vectors/` are consumed by both the Rust and Swift suites so the two implementations cannot drift; change them in lockstep.
- `plugin/` also ships the Host Tools for tmux and herdr Hosts: `bin/waycar`, the static native binary built from `plugin/rust` (built with cargo and cargo-zigbuild and copied into the package; `plugin/bin/` in the repo holds only `waycar-hook`), and `bin/waycar-hook` (POSIX sh Status Hook). The binary runs `pair`, `hooks install|uninstall|status|migrate`, `status [--json]`, `version`, the hook runtime (`notify`, `watch-approval`, `hook-session`, `herdr-event`, `herdr-startup`, `activity-tick`), the app's readers (`chat-read`, `chat-media`) and `config-dir` (prints the plugin config dir; the opencode and kilo chat-prompt extensions run it). The Host needs no Node (ADR 0031). Agent hook entries call `'<root>/bin/waycar' hook-session <agent> [event]` and `'<root>/bin/waycar-hook' <agent> <status>`; the herdr manifest runs `./bin/waycar herdr-startup` and `herdr-event`. `install.sh` stages the package, runs `bin/waycar version`, swaps it in, runs `waycar status --json`, and restores the old install on failure. It installs herdr mode when herdr is on PATH, tmux mode otherwise or with `--tmux`, and with tmux 3.2+ links `~/.local/bin/waycar` and installs the Status Hooks unless `--no-hooks`; `WAYCAR_PLUGIN_SOURCE` installs from a local `plugin/` with a built `bin/waycar`. The pane-option contract is pinned by `plugin/test-vectors/tmux-pane-options-v1.json` (Rust and Swift).

## Load-bearing herdr facts

Rediscovering these is expensive. Each fact retains its evidence version and method (live observation or source review); older observations are not re-tests on a newer release. For 0.9.0 subscription ordering, compatibility evidence, and remaining verification, read [the integration review](docs/research/herdr-0.9.0-compatibility.md).

- The herdr API socket serves **one request per connection** (read one line, write one line, close). Only `events.subscribe` keeps the connection open. Plan channel usage accordingly. (Re-verified live on 0.8.0: a second write on a served connection gets `EPIPE`. `pane.graphics.stream`, previously listed here, does not exist in the 0.8.0 schema — graphics methods are `pane.graphics.set`/`clear`/`info`, all one-shot.)
- Wire format: request `{"id": "<any string>", "method": "...", "params": {...}}` + `\n`; `params` is required, and `{}` satisfies it. Success `{"id", "result"}`, failure `{"id", "error": {"code", "message"}}` (both re-verified live on 0.8.0), subscription event lines `{"event", "data"}` with no id.
- The first message on any new connection path should be `ping` — it returns the server protocol version (0.8.2 answers `{"version":"0.8.2","protocol":20,...}`; 0.8.0, verified live, answered `{"version":"0.8.0","protocol":19,...}`). herdr's API has no stability guarantee; parse leniently (ignore unknown fields). The app enforces a **floor**, not equality: `WaycarSSHTransport.minimumProtocolVersion` refuses older servers, `generatedProtocolVersion` only drives an advisory notice. Equality here made every 0.8.0 Host unusable (#140) — do not restore it.
- The API schema is exported offline via `herdr api schema --json` (JSON Schema 2020-12). Its `$ref` paths are non-standard nested (`#/schemas/request/$defs/X`) — preprocess before feeding codegen tools. The committed 0.9.0 snapshot (protocol 22) declares 102 request methods and 26 event kinds (its event and subscription-event schemas are unchanged from 0.8.2), and every one of those kinds has a typed `EventData` variant; separately, 3 pane-scoped kinds (`pane.output_matched`, `pane.agent_status_changed`, `pane.scroll_changed`) have typed `SubscriptionEventData`. Payloads herdr actually emits are still worth verifying empirically.
- Pane ids are opaque strings. Protocol-22 `scripts/herdr-schema.json` declares `pane_id` as a string with no `pattern`. Observed herdr 0.7.5 captures (`w1:pA`, `w3:pB`, `wV:p1`) and live 0.8.0 `agent.list` samples (`w1:pT`, `w1C:p1`, `wR:pC`, `wV:p1H`) are alphanumeric `w…:p…` identifiers and include uppercase letters. Those captures contain no tmux-style `%N`; that does not prove herdr can never emit it. Treat every pane id as an opaque string; do not parse or validate a grammar.
- SSH exec channels are session channels, capped by sshd's `MaxSessions` (default 10) per connection. All RPC traffic must go through a request queue that bounds concurrency.
- `herdr agent attach` requires a TTY (ratatui). It works over an exec channel only when a PTY is requested.
- herdr 0.7.5 tightened `agent.start` (verified against a live 0.7.5 server): the kind must be on its supported-agent list (arbitrary commands like `bash -i` are rejected with `unsupported interactive agent kind`), and a freshly created pane is rejected with `agent_pane_busy` ("not an available shell") until its shell reaches the interactive prompt — a few seconds. The transport retries on that code; see `WaycarSSHTransport.startAgentAwaitingShell`. On 0.8.0 `agent.start` is asynchronous instead: it returns `launch_pending: true` immediately (verified live 6ms after pane creation) and `agent_pane_busy` did not occur. On 0.9.1 it is back: the herdr server log shows it on phone launches, and it was reproduced against a live server. A tab whose shell rc is still running (e.g. a 1 s autostart countdown) is refused once or twice before a retry is accepted, so the retry path is live again.
- Default remote socket: `~/.config/herdr/herdr.sock` (still the path a live 0.8.0 server serves); named sessions live under `~/.config/herdr/sessions/<name>/herdr.sock` (not re-tested on 0.8.0). Resolve `$HOME` over exec once per Host; Waycar remembers it on the device per connection target (`<host>.connection.json`, `HostConnectionMemory`, #105) and re-resolves it once when the remembered path's socket is missing (`retryingAfterHomeRefresh`).
- `AllowTcpForwarding no` also blocks direct-streamlocal (OpenSSH `channel_disable_admin(FORWARD_LOCAL)`), whatever `AllowStreamLocalForwarding` says, so a herdr Host needs `AllowTcpForwarding local` or `yes` — verified live on Linux test Hosts.
- If the herdr server is not running, connecting to the socket fails outright; there is no auto-start on the socket path. `herdr remote-client-bridge` (the wake command) starts the server and the socket, and the server outlives the exec channel (live, Ubuntu 24.04 Docker Host, herdr 0.9.5, 2026-10-27).
- The woken server, and every pane it starts, inherits the wake exec's environment (live, macOS, herdr 0.9.5, #389). A plain SSH exec wake came up in 0.36 s, but its panes had `LC_ALL=C` (the exec's old `cLocaleCommand` wrap, since dropped from the wake), `SSH_CONNECTION`, no SSH agent, and a locked login Keychain ("User interaction is not allowed"). The same wake as a one-shot launchd job bootstrapped into `gui/<uid>` from SSH gave panes no `LC_ALL` or `SSH_CONNECTION`, `SSH_AUTH_SOCK` through herdr's agent relay and an unlocked Keychain, but a cwd of `/` (hence the job's `cd "$HOME"`), and the server survived the job's exit and `bootout`. A job without `ProcessType` runs throttled, and so does everything it spawns, setsid'd daemon included (a stand-in server and its child at priority 20, against 31 from an SSH exec; live, macOS 27.2, 2026-11-10); `ProcessType` `Interactive` gives 31. So on macOS with a logged-in user the wake runs as such a job (`WaycarSSHTransport.wakeExec`, `SSHTransportSettings.wakesInLoginSession`, off in real-SSH fixtures, which run on a developer's Mac), falling back to the plain wake when launchd refuses it. The wake runs only when the user asks (next fact).
- herdr's installer (`herdr.dev/install.sh`, 150 lines, 0.9.5) downloads and checks a binary into `~/.local/bin` and starts **no server**: after it, `~/.config/herdr` does not exist and a direct-streamlocal open fails (`channel open failed`). The same holds after a Mac restart: herdr's server exits (session saved) and nothing restarts it (#389). `classifyStreamLocalOpenFailure`'s one exec reports a missing socket as `.herdrNotRunning` when `herdr` is on the wake's PATH and the session exists (the default session, or the socket's folder), as `.herdrSessionNotFound` when herdr is there but a named session's (or custom path's) folder is missing, and as `.socketNotFound` with no herdr. Waycar never wakes herdr on its own (#389, the user's decision: no service starts on a Host without a tap): requests, the events subscribe, reconnects and attaches only report `.herdrNotRunning` and the stale-socket `.streamLocalOpenFailed`, and the Console row and Host page offer **Start Herdr TUI** for exactly those two (`ConsoleStore.startRuntime`, through `TransportConnector.wakeHerdr`; `TransportError.startableRuntime` decides the offer), which runs the wake once and reconnects the herdr scope; a failed start shows herdr's stderr (`HerdrStartError`). herdr counts a named session only once `~/.config/herdr/sessions/<name>/` exists, and `HERDR_SESSION=<name> herdr remote-client-bridge` would create it (source review, `session.rs` `list_sessions`), hence the folder rule: `.herdrSessionNotFound` is never offered a start. The one start without that tap is Backend Install's, right after the user taps Install herdr and a herdr install is found (`BackendInstallCenter`): `ping` then answers and `workspace.list` returns one default workspace `~` (live, same Host). Check Again in the install panel starts nothing. A bare SSH exec has no `~/.local/bin` on PATH, so detection and the install exec add `HerdrHostPath.extraPATH`. The installer's own `printf | awk` pipelines print `printf: I/O error` when SIGPIPE is ignored, so the herdr install exec never ignores it. `curl … | sh` exits 0 when curl fails (live: `curl: (7)` then `pipeline exit=0`), so the installer is downloaded to a temp file first.
- `herdr agent attach` resolves its target against **agents only**: attaching a plain shell pane fails with `agent_not_found` (verified against a live 0.7.5 server; resolution unchanged in the 0.8.2 source). Ordinary terminals attach with `herdr terminal attach <terminal_id> [--takeover]` instead (0.8.2, verified against the installed CLI and the `v0.8.2` source tag): after resolving the Agent's `terminal_id`, `agent attach` enters this exact same client path (`src/cli/agent.rs` → `run_terminal_attach`). The text lives at `result.read.text` (nested), not top-level.
- Output-change signals, verified live on 0.8.0: `pane.output_matched` is edge-triggered — one push when the visible buffer's match predicate flips no-match→match (plus one at subscribe time if already matching), silence during sustained output — useless as a change feed. `pane.agent_status_changed` is the precise push signal (two ~125-byte events per prompt round trip). `pane.updated` remains a ~4/s noise source. `events.wait` implements only pane agent-status matches despite the schema declaring 19 `EventMatch` variants, and its param is `match_event` (a single object).

- An attach **owns the pane's size until it exits** (herdr 0.9.1 source review of `v0.9.1` plus a live probe). `herdr agent attach` / `terminal attach` resizes the pane PTY to the attach client's winsize and holds a resize lock (`src/server/headless.rs:1848-1899`); nothing the desktop TUI does reclaims it while the attach lives. - herdr 0.9.3 (verified live) rejects any `agent.start` arg containing a newline or tab with `invalid_agent_argument` ("agent arguments cannot be encoded safely for the target shell"); every other character is shell-encoded by herdr. So Waycar collapses whitespace in the Chat Prompt to single spaces (`ChatModePrompt.launchText`).
- herdr 0.9.3 polls a new API connection's first request line every **100 ms** (source review of `v0.9.3`: `src/api/server.rs:29` `CONNECTION_POLL_INTERVAL`, the non-blocking read and sleep in `read_initial_request_line_with_limits`, `:699-743`): a request already queued at accept is answered at once, anything later waits for the next tick. Over SSH the request always lands at least one round trip after sshd's connect, so every one-shot RPC pays about 100 − (RTT mod 100) ms: measured live on 2026-10-03, a ping sent 5/20/150 ms after accept took 94–104/73–82/49–64 ms on the local socket, and ping and snapshot took 102–110 ms each through `ssh -L` at a loopback RTT. An accepted connection that sends no full request line within **5 s** is closed (`INITIAL_REQUEST_TIMEOUT`, `server.rs:31`; measured live: EOF at 5.04 s), so a pre-opened herdr channel must be used within about 4.9 s and still waits for its tick. No client-side fix exists over direct-streamlocal; an upstream fix (a `poll(2)` wait instead of the sleep, local branch `api-immediate-request-read` in a herdr checkout, unpushed) answered in 0.0–0.4 ms in the same benchmark.
- A herdr server restart restores the session (verified live on a 0.9.1 → 0.9.3 upgrade, `persist.restore` in the server log): every pane keeps its pane id, every terminal gets a **new** terminal id, and each Agent is resumed in its new terminal through herdr's integration (`omp --resume=<session path>`), **without** its original launch arguments, so a Chat Mode Agent loses its Chat Prompt. herdr reports the same `agent_session` for the resumed Agent. - `pane.process_info {pane_id}` (since herdr 0.7.0, protocol 14; verified live on 0.9.3 and by source review) returns `shell_pid`, `foreground_process_group_id` (the shell tty's foreground pgrp: `/proc` tpgid on Linux, `e_tpgid` on macOS; null when herdr finds no foreground job) and `foreground_processes` (that pgrp's members; Linux lists them by pid, `name` is the 15-char comm and `argv0` is null; `tty` is always null). ## Load-bearing tmux facts

Verified live on tmux 3.7c (Homebrew, private `-L` servers, locally and over `ssh -T localhost`) unless noted; hook facts from live runs of Claude Code 2.1.286 and Codex 0.159.2; version floors from tmux `CHANGES`/source tags. Full table and consequences: `docs/design/tmux-backend.md` §1; research in `docs/research/tmux-backend-2026-09-30.md`.

- `tmux -C attach` runs on a non-PTY exec channel; `-CC` fails without a tty (`tcgetattr failed`). `-u` is required over SSH exec or tmux draws non-ASCII as `_` (implementation). (T1)
- Each `;`-separated command gets its own `%begin <t> <n> 1` … `%end`/`%error` block, in send order; notifications arrive only between blocks; `<n>` is server-global — match FIFO, never by number. (T2) A failing command in `a ; b ; c` drops the rest of the line: one `%error` block, none for the rest (implementation). `%config-error` arrives inside the attach command's own reply block (implementation).
- A control client must stay attached: `-C list-sessions`/`new-session -d`/`start-server` print and exit; with no sessions `-C attach` answers `no sessions` (rc 1). (T3)
- `attach -f no-output,no-detach-on-destroy` works; `-f` since 3.2, `no-detach-on-destroy` since 3.6; unknown flags dropped silently (`#{client_flags}` shows what applied). Below 3.6 reattach on `%exit`. (T4)

## Load-bearing Codex facts

Full X1–X25 evidence (Codex 0.167.1, live checks and source review) is in [`docs/design/codex-backend.md` §1](docs/design/codex-backend.md#1-load-bearing-codex-facts); the executable pin lives only in `scripts/ci/codex-contract.py`.

- Detection (`codex --version`, `codex app-server daemon version`) starts no server. Only an explicit **Start Codex server** may run `daemon start`; a stopped server is offered in Host detail and New Agent, never the Console. Recheck an installed/stopped server on connection or foreground. Codex below 0.167 needs an update. (X1, X3)
- The advertised control socket links into `/tmp/codex-daemon-<uid>/`, with a canonical-path hash and startup lock. A scratch HOME alone does not isolate it: use a unique canonical CODEX_HOME, and never stop the developer's server. The complete npm package is required to start a managed server. (X2–X4)
- The tokenless WebSocket requires an `initialize` request before RPCs; each text message is one JSON object. Use direct-streamlocal, which needs `AllowTcpForwarding local` or `yes`, as for herdr. (X5, X6)
- List loaded ids and read metadata without resuming just to list: a subscription keeps a thread loaded. With no subscriber or active turn it unloads after 60 s by default, becomes a Closed Session, and resume reloads it. A TUI resume of an unknown thread emits status, not `thread/started`. (X8, X18, X19, X23)
- Turn/item events and approval requests go only to subscribers; all clients see thread status. Resume replays pending approvals, and `serverRequest/resolved` removes one answered elsewhere. (X17, X19, X22)

Chat falls back on server refusal to `thread/read {includeTurns: true}`, retaining the newest 200 turns with the same builder; ordinary paging is capped at four pages. Both methods may refuse before materialization, so refresh still retries. (X25)
- Thread origin is `threadSource`: a plain desk TUI sends `user`, Waycar starts send `waycar`; both can report `source: vscode`. Only `user` threads enter same-folder terminal linking, and only empty unnamed `waycar` threads enter lost-create adoption. Unknown origins do neither. The tag survives unload and reload. (X24)

## Load-bearing SSH, mosh and terminal facts

Same rule as above: each fact keeps its version and method.

- mosh-server 1.4.0 starts the wrapped command only after the **first client datagram** (source review of `src/frontend/mosh-server.cc`): after `forkpty()` the child blocks reading its PTY, and the serve loop writes the newline that releases it only once a client state advances its remote-state counter (`:593-597`, `:822-828`). A server that never hears from a client **exits after 60 s** (`:682`, `:914-918`). So a mosh-server started ahead of its client (a Standby, ADR 0027) runs no `herdr agent attach`, holds no resize lock and needs no cleanup. The same release explains why nothing Host-side happens between the banner and the client's first datagram (#27). It ignores SIGHUP and SIGPIPE once it has printed `MOSH CONNECT` (source review; observed live with `executeUntilLine`), so ending the bootstrap exec early does not kill it.
- Waycar's libssh2 (snapshot `c7557852`) carries four reviewed patches (`Packages/WaycarSSH/Patches/libssh2/`, hashes in `Sources.lock` and `Artifacts/PROVENANCE.md`): `0001` signs publickey auth without the `PK_OK` query, `0002` sends pty-req and exec back to back, `0003` fixes `ssh2_packet_requirev()`, `0004` adds per-channel pipelined opens. Measured by `make test-libssh2-patches` against OpenSSH 10.3p1 behind an 80 ms RTT proxy (2026-10-03, best of 3): auth 218–234 → 117–132 ms, PTY plus exec 192 → 93 ms, four stream-local opens 366 → 95 ms. A refused or abandoned pipelined open is freed without costing the session; an unauthorized key is now signed before it is refused (sshd logs no `test pkalg`).
- Upstream libssh2 `ssh2_packet_requirev()` (at `c7557852`) fails a channel-filtered wait with -1 when the packet it reads is a wanted type for **another** channel, instead of leaving it queued and reading on (source review; reproduced in the patch tests, where dropping `0003` makes a pipelined open return -1). Anything that overlaps channel requests on stock libssh2 hits it.
- libssh2 `c7557852` queues `CHANNEL_OPEN_CONFIRMATION`/`FAILURE` and `CHANNEL_SUCCESS`/`FAILURE` packets untouched in `_libssh2_packet_add`, and `packet_requirev` checks that queue by local channel id before reading the socket (source review), so an opener may release the session mutex while it waits as long as no stock open (SFTP init) starts meanwhile.
- OpenSSH sends **no `CHANNEL_CLOSE` while a non-PTY child is alive**, even after the client's EOF (observed in the WaycarSSH E2E lane against OpenSSH 10.3p1, 2026-10-03). A PTY-denied command that ignores stdin EOF therefore holds its channel until the 2 s cleanup budget invalidates the session; the old response-line `sleep 30` timeout test invalidates the same way.
- Ghostty draws with Metal into an IOSurface that its `IOSurfaceLayer` sublayer shows as `contents`; `drawHierarchy` draws that layer **black**. `TerminalFrameCapture` reads the presented IOSurface instead (libghostty-spm 1.6.20260909 on the iOS 27 simulator, 2026-10-03; `AgentLastFrameEntryTests` finds a real multi-colour frame). A frame of a 13-inch iPad terminal at 2× is about 100 KB as JPEG quality 0.6.
- On Darwin a loopback port that is bound but not listening drops a SYN silently, which makes a deterministic connect blackhole for tests; a port nobody holds refuses at once, and a listen-backlog overflow resets (`ECONNRESET`). The kernel gave up on an unanswered loopback SYN after about 7.8 s (macOS host, observed 2026-10-03 in `SocketConnectorLoopbackTests` work).
- mosh-server 1.4.0 builds a new state on the client's **last acknowledged** state, not the newest it sent, whenever acks trail its patience, which is routine at a few hundred ms RTT; its diff skips cells the base and new state share and scrolls with LF, so a client must apply each diff to its stated base, never to the newer screen it already shows. SwiftMosh keeps recent screens (`MoshScreen`, Waycar patch 16) and repaints Ghostty from them for an older-base state. Measured 2026-10-07 by `testRealMoshServerStatesOnOlderBasesLeaveTheTerminalRight` (300 numbered lines, every client datagram 150 ms late, local mosh-server 1.4.0): 63–73 older-base states per run; the terminal ended exact, where applying them on top left 11–18 of 24 rows wrong.
- The client screen model's character widths must equal the Host's `wcwidth`, which mosh-server lays out with: a 1-column disagreement shifts every later cell, the model keeps it until the server redraws those rows, and every older-base repaint paints it into Ghostty. Wide scalars come from `MoshCharacterWidthTable`, generated from Darwin's `wcwidth_l` (en_US.UTF-8, Unicode 15.0, macOS 27.0.1 26A434, recorded in `sourceDescription`) by `Packages/SwiftMosh/Scripts/generate-character-widths.swift` (`--check` for drift). A glibc Host differs on a few scalars (U+3248–324F and U+4DC0–4DFF are 2, among others; listed in `MoshCharacterWidth`'s doc comment from a source review of glibc's `utf8_gen.py`). Verified 2026-10-07 (#148, local mosh-server 1.4.0 on macOS 27.0.1, one run each): the old hand-made emoji ranges counted 👁 (text presentation, 1 column on the Host) as 2, so omp's full-width status row (two 👁) autowrapped the model and drifted every later row; `testRealMoshServerOlderBasesWithFullWidthSymbolRows` (that row scrolling, 150 ms late uplink) left 19 of 24 rows wrong with the old widths (24 older-base states) and 0 with the table (27). Its stand-in terminal is a `MoshScreen`, which shares the width function under test.

## Conventions

- Build, test, device installs, and TestFlight uploads all go through `make` (see `make help`). An interim TestFlight build is `make bump && make testflight` — App Store Connect rejects reused build numbers. Interim builds (`make testflight`, the CI TestFlight workflow) compile in the admin panel (Settings › Admin) with `ADMIN_BUILD=1`; `make publish` never does, and only its build may go to App Review (ADR 0032, `docs/guides/releasing.md`).
- Every build installed on your iPhone (`make install`) or iPad (`make install-ipad`) carries a local What's New, because several worktrees build to the same device: install with `make install NOTES=<file|auto>` (and `make install-ipad NOTES=…`); every device build must carry notes. The file is one `symbol|text` (or plain text) line per item saying what to test; `auto` uses the commit subjects since that device's last local install. `scripts/write-local-whats-new.sh` writes `Sources/Waycar/Resources/WhatsNew.json` with a unique `id` (a DEBUG build shows it once whatever the build number, without moving the TestFlight build marker) and the install always restores the committed `{"builds": []}` seed; never commit local notes. A self-build for one person's own phone (`make install TEAM=…`, `docs/agents/build-to-your-iphone.md`) needs no notes.
- Cutting a release is `make publish` (`scripts/publish.sh`, documented in `docs/guides/releasing.md`): it moves `CHANGELOG.md`'s `[Unreleased]` body into a new `apps/web/src/content/changelog/<version>.md` (one file per release, shown on waycar.dev/changelog and in the app's Settings › About › Changelog), bumps `MARKETING_VERSION` in `project.yml`, builds and uploads to TestFlight, then tags and creates the GitHub release, and last runs `make distribute` to add the release build to Waycar Testers (a failure there leaves the release complete and prints `scripts/asc-distribute-build.py <build>`). `[Unreleased]` is the source of the notes and the release files' `version` front matter is the record of released versions; never hand-edit `MARKETING_VERSION`, write a release file, or create a `vX.Y.Z` tag by hand. - A lifecycle spread over flags, optionals, Task handles or counters becomes a `StateMachine` (pure `handle(_:) -> [Effect]`, tokens across `await`); `docs/design/state-machines.md` has the convention, the index of every machine and the catalogue of the rest, and `scripts/check-state-machines.py` (`make test-app`, CI) fails when a machine is missing from the index.
- App tests wait for something to happen with the shared `waitUntil` (`Tests/WaycarTests/Support/TestWaits.swift`: `Task.sleep` polling, the 30 s `Duration.waitCeiling`, first success returns), never a fixed sleep, a `Task.yield()` loop or a private copy with a short deadline: CI's test host stalls for seconds on a loaded Mac. The condition must be one only the awaited state satisfies: a status or count the code also reaches early (a resnapshot after a resubscribe) is counted from a baseline taken before the action. Short windows only assert that something does *not* happen; a window the code measures takes an injected clock. Other builds into that DerivedData (`make sim`, `build-sim`, `build`, `build-device`, the e2e scripts, `make screenshots`) run the gate non-fatally and touch offenders. Make pure members `nonisolated`, or make the caller `@MainActor`.

When updating: diff and re-apply the `Sources/` patches; in the script set the new libghostty-spm commit, the Ghostty commit from that commit's `Ghostty.ref`, and the Zig version its build needs; check the 0100 patch still applies, regenerating it with `git diff --full-index` from a clean Ghostty checkout (not the build tree, which carries libghostty-spm's own `SharedDeps.zig` edits); update the package pins in `Scripts/collect-libghostty-licenses.sh`; rebuild; copy the scripts, patch and `LICENSES/` into `otreva/ghosttykit` and publish a new release there (tag `<libghostty-spm release>-<Ghostty short commit>-nointl.<n>`) with the zip and `LICENSES.zip`; set `Package.swift`'s `libghostty` URL and checksum and record the checksum in `PROVENANCE.md`; then run `make test-app TEST_FLAGS='-only-testing:WaycarTests/TerminalTouchInteractionTests -only-testing:WaycarTests/TerminalMouseReportingTests'`.
- `Packages/SwiftMosh` is vendored swift-mosh plus the Waycar patches listed in its `PROVENANCE.md` (ADR 0021). `make test` runs its package suite on the Mac host via `make test-swiftmosh` (`swift test --package-path Packages/SwiftMosh`); its real-server tests skip there. CI's SwiftMosh job runs them with `SWIFTMOSH_REAL_E2E=1` against a brew-installed `mosh-server` and fails when any of them skips. When updating, re-apply the patches and run that real-server suite too, which needs a local `mosh-server`: `SWIFTMOSH_REAL_E2E=1 swift test --package-path Packages/SwiftMosh`. Never link, copy or port mosh's own GPL code into the app: Waycar is Apache-2.0.
- mosh-server 1.4 acks a client state with an empty diff only on its 3 s ack interval (`networktransport-impl.h`); a non-empty one is acked within 100 ms. So the stall pill waits 6.5 s of silence (`MoshAttachSession.stallThresholdMs`, mosh's own `server_late` is 6500 ms), and anything that needs an answer now (a rebind, the contact check on return) sends `elicitServerReply()` (patch 15), a repeat of the last sent size. When a stalled server answers again, the Console redials that Host's disconnected connections at once (`ConsoleStore.moshServerAnsweredAfterStall(on:)`).
- Tracker is GitHub issues in this repo (`gh issue ...`). Reference issues from commits with `refs #<n>`.
- User-visible changes get a `CHANGELOG.md` entry under Unreleased, referencing the PR; `make publish` moves them into that release's file. Entries are published verbatim at waycar.dev/changelog and in the app, so write them for users and keep internal paths, ADR numbers, hostnames and real user or customer data out of them (issue refs are fine; they are stripped on display). Internal refactors and test work stay out of it.
- Every change to a file the plugin package ships (`plugin/bin`, `hooks`, `herdr-plugin.toml`, `install.sh`, the tmux pane-option vector, the Rust crate `plugin/Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `rust/`, `scripts/package-plugin.sh` and `scripts/build-plugin-binaries.sh`; not README/LICENSE/NOTICE) bumps the plugin version in `plugin/herdr-plugin.toml` and `plugin/Cargo.toml` (+ `Cargo.lock`, refreshed with `cargo update -p waycar --offline` in `plugin/`) and `WaycarPluginRequirement.currentVersion`, which Host detail offers to older Hosts as "<version> available" (an offer, never a gate): patch for fixes, minor for new behavior. An app change that relies on new plugin behavior raises `WaycarPluginRequirement.minimumVersion` (`Sources/Waycar/Transport/WaycarPlugin.swift`) in the same PR; the app then prompts users to update older Hosts. `scripts/check-plugin-version.sh` (CI, and before web.yml deploys and plugin-release.yml tags) checks that the version fields and `currentVersion` agree, the minimum is not above the plugin version, and shipped files (incl. `scripts/package-plugin.sh`) are unchanged since the released version (the `plugin-v<version>` tag, or the `PLUGIN_BASE` baseline when it already has this version); on merge `plugin-release.yml` cuts `plugin-v<version>` and waycar.dev/install.sh serves `main`'s plugin (`docs/guides/releasing.md`).
- `WaycarPluginRequirement.nativeToolsMinimumVersion` (2.0.0, the first native plugin) only prompts Hosts on the Node-era plugin to update; it is never a gate, so never read it to turn a feature off and never raise `minimumVersion` for it. `WaycarPluginRequirement.coreMinimumVersion` (2.2.0, the first plugin with a herdr-core mode) is read only for a Host whose resolved backends include core (`status(of:backends:)`, `ConsoleStore.waycarPluginStatus`), so a Host without core keeps the old minimum. The app build that carries either, or `currentVersion`, must not ship before waycar.dev serves a plugin at least that new: `make archive` runs `scripts/check-deployed-installer.sh` first and fails otherwise (`docs/guides/releasing.md`).
- Update `CONTEXT.md` when domain terms change; add an ADR only for hard-to-reverse, surprising trade-offs.
- Brand look and voice live in `DESIGN.md`: every color, gradient, font, radius, and shadow comes from `design/tokens.json` via `scripts/generate-brand-tokens.py` (web CSS + `Sources/Waycar/Design/BrandTokens.swift`); never hard-code a brand value.

## Analytics (PostHog)

PostHog US project 631477 ("Waycar") holds app and waycar.dev events. To answer traffic or usage questions, source `~/.env` and POST HogQL to `$POSTHOG_HOST/api/projects/$POSTHOG_PROJECT_ID/query/` with `Authorization: Bearer $POSTHOG_PERSONAL_API_KEY` (read-only key), or use the `posthog` MCP server. Always exclude non-customer traffic unless asked otherwise: `properties.env = 'release'`, `properties.likely_bot` not true (headless browsers), and `properties.internal` not true (the owner's browsers, set by visiting `waycar.dev/?internal=1`). For Trends/insight queries set `filterTestAccounts: true`, which applies the same three filters. `plugin_install_requested` events with `properties.internal = true` are ours: our own tooling fetches `https://waycar.dev/install.sh?internal=1` (the query changes only the event, not the script), so our automation and dev fetches must use that URL, while user-facing install instructions keep the plain one. Page views before 2026-09-28 16:30 UTC predate the bot tag: treat 800x600-screen visits with a UTC or unknown time zone as bots.

`plugin_package_downloaded` (the tarball `install.sh` fetches; `via` = `install` or `pair`, `kind` = `install` or `update`, both set by `install.sh`) follows the same rule, and the query on `install.sh` does not reach it: a script that downloads the package itself must add `?internal=1` to that URL, and an `install.sh` run by our automation needs `WAYCAR_INTERNAL=1`. `plugin_install_requested.kind` is set only when the caller sends `?kind=`, so most rows have none. `plugin_install_requested` counts script fetches, `plugin_package_downloaded` installers that reached the download (pair-only runs and in-app Plugin Updates included).

Network analytics (`host_connect`, `terminal_attach`, `transport_lost`, `app_foregrounded`; ADR 0027; `host_connect.trigger` is `launch`, `foreground`, `retry`, `path_change` or `mosh_recovery`) go out only from internal builds, Debug and `ADMIN_BUILD=1` (`BuildFlavor.current`), and in a release-configured build only once a verified receipt shows a non-production environment (`AppEnvironment.allowsAdmin`); all of it stays behind the opt-in. Until that receipt check resolves, such events are dropped, not queued. The PostHog `env` property reads `release` in admin TestFlight builds too, so filter those events by name, not by `env`. Every build logs network phases without host data: `log stream --predicate 'subsystem == "com.otreva.waycar" && category == "network"'`, and Instruments shows the signpost intervals (ssh dial/handshake/auth, connect, first channel, ping, revalidate, subscribe, snapshot, terminal attach, standby mosh, mosh stall).

## Running tests

- Everything goes through `make` (`make help`). `make generate` regenerates `Waycar.xcodeproj` from `project.yml` (XcodeGen), and every build target does so first.
- `make test-app` runs the app suite on the simulator `SIM` (default iPhone 17 Pro Max); one suite with `TEST_FLAGS='-only-testing:WaycarTests/<SuiteTypeName>'`. `make test` adds the `Packages/WaycarSSH` suites and `make test-swiftmosh`; `make test-ipad` runs it on `SIM_IPAD`. `cargo test --locked` in `plugin/`, `npm test` in `relay/` and `apps/web/`.
- Simulator targets lease their simulator through `scripts/sim-slot.py` (Simulators, above); alone on a Mac it grants one at once. `make sim-status` shows the queue, `make sim-release` frees yours once you are done.
- Suites that need a real SSH server skip cleanly without their fixture; CI (`ci.yml`, GitHub-hosted macOS) provisions disposable sshd instances and runs them all, and `make test-ci-app` runs that lane on your Mac (`WAYCAR_CI_PASSWORD_FIXTURE=0` skips the one fixture that creates a temporary macOS account). `make test-tmux-remote BOX=<distro>` runs the tmux suite against a Linux box built from `scripts/testboxes/` (`WAYCAR_TESTBOX_HOST` names its Docker host), and `make test-harness-lab` the agent-harness lab (Harness lab, above); both run only where one is configured. App test runs fail when the run's simulators left Waycar crash reports (`scripts/check-crash-reports.py`): investigate each one.
